Workflow Design Summary: CMS Block Design-to-Implementation

Turns a design input for one CMS block — a mock, a written spec, or even a one-line request — into a working, tested block component in the PlentyONE Shop PWA codebase.

1The task

Unit of work per run
One CMS block, from whatever design input exists (image, text spec, or one-liner)
"Done" looks like
Working block: real code + passing unit tests + lint/typecheck clean — not yet a PR
State of design docs
None pre-exist (confirmed) — the spec is created fresh, every run, via interview

2Structure — 2 skills, flow, and freedom

Skill 1: designing-cms-blocks
Interview-driven spec + mock creation. Owns its own context window — open-ended back-and-forth before any code exists.
1 · InterviewHigh
Extract what's given from the input (image/text/one-liner); ask for whatever's undetermined: content vs structure, category, accessControl, settings fields + grouping, which editor widget per field, simple vs complex form. Runs scripts/list-components.sh for a live list of real available components instead of consulting a hand-maintained catalog.
2 · Write specLow
Fill assets/block-spec-template.md with the interview's answers.
block-spec.md
3 · Build mockMedium
Single-page static HTML with two sections — the rendered block, and its editor form — from assets/mock-template.html (Tailwind CDN + inline config copying real static design tokens from tailwind.config.ts; primary/secondary are placeholders since real brand colors are runtime CSS vars).
mock.html
STOP — Checkpoint 1
User approves block-spec.md + mock.html together before any code is generated. Approve, not co-build — wrong content/structure or accessControl calls are expensive to unwind after scaffolding.
→
block-spec.md + mock.html
Skill 2: implementing-cms-blocks
Fresh context. Reads only block-spec.md and mock.html — no memory of the interview.
4 · ScaffoldLow
Run npm run generate:block via the existing code-generation skill, with flags derived from the spec (--structure, --category, --access-control, --complex-form) using a deterministic mapping table in SKILL.md.
5 · ImplementMedium
Fill defaults.ts, types.ts, <Block>.vue, <Block>Form.vue, and a block-layout.config.ts override if needed. mock.html is the visual reference; references/block-conventions.md supplies the real code patterns.
Conditional If a widget or pattern not already in references/block-conventions.md is needed, append it there after implementing.
6 · TestHigh (mandated)
Write real unit tests for the spec's fields/behavior. Existing blocks (ItemData, Carousel) skip tests — this workflow does not get to copy that.
7 · VerifyLow
npm run lint, npm run typecheck, npm run test. No automated visual diff — mock.html serves Implement only, not Verify.
STOP — Checkpoint 2
User reviews verification results (green lint/typecheck/tests) and the finished file list before opening a PR themselves.
High freedom — prose/heuristics Medium — template-driven Low — strict template / exact steps STOP — checkpoint (human in the loop) OUT: output artifact
Determinism: Scaffold reuses the existing code-generation skill's generate.sh — no new script needed there. scripts/list-components.sh (intake) enumerates real component names from components/editor, components/ui, and node_modules/@storefront-ui/vue/dist/components — ground truth instead of a maintained catalog that can drift. The spec-field → CLI-flag mapping is a fixed table in SKILL.md, not model judgment.

4Alignment — struggle points and checkpoints

Over-/under-asking during the interview, or misclassifying content vs structure
fixed by
block-spec-template.md's fixed section list
Every section must be filled; the template drives what's asked, not open-ended judgment.
mock.html drifting from the real design system
fixed by
mock-template.html's Tailwind CDN + copied tokens
Forces real colors/spacing/type scale instead of arbitrary CSS guesses.
Implementation drifting from established block conventions (skipped EditorFormPanel grouping, missing en/de duplication)
fixed by
references/block-conventions.md, mandatory read before writing Form.vue/.vue
Forces pattern reuse instead of inventing a new shape per block.
Tests get skipped or shallow — real precedent (ItemData, Carousel) has none
fixed by
Test step mandated explicitly in SKILL.md
Coverage is required regardless of what neighboring blocks do.
Checkpoints: Checkpoint 1 (end of block-design-intake) — approve block-spec.md + mock.html together, before any code is touched. Checkpoint 2 (end of block-implementation) — review green lint/typecheck/tests + finished file list before the user opens a PR themselves.

5Verification ladder

Minimum bar
Lint + typecheck clean
npm run lint, npm run typecheck
Stronger
Real unit tests, passing
Written per the spec's fields/behavior, run via npm run test
Strongest
None — declined
Automated visual diff and adversarial review were both considered and dropped; single-block scope doesn't earn the cost.
Multiple perspectives (agents): No — single block, low blast radius, one pass suffices.
