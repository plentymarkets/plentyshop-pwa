Flag naming convention

extension.<extension-id>.enabled  →  extension.plenty-pwa-module-prototype.enabled: false

Absent key = enabled. Only an explicit false disables. Written to and read from flags.json (path set via JSON_FEATURE_FLAGS_FILE env var, same in dev and production).

Three ways a module can participate

Pattern A — Slot injection

  • Module calls register() in a plugin at startup
  • PWA places <UiExtensionSlot name="homepage-top" />
  • getSlotEntries() filters by feature-flags state
  • Component disappears instantly when toggled off — no refresh
  • Module effort: one register() call

Pattern B — New page

  • Module adds route via extendPages (standard Nuxt)
  • shop-core tags the page with extensionId in pages:extend
  • extension-guard middleware redirects to /not-found
  • Page optionally calls showError(404) as SSR guard
  • Module effort: none for routing — standard pages.push()

Pattern C — Page override

  • Module swaps an existing PWA page file (/checkout, /terms-and-conditions)
  • Original saved as Nuxt alias (#pwa-checkout-original)
  • Replacement uses v-if="isEnabled" to switch between module UI and original
  • Instant switch — v-if reacts to flag change with no refresh
  • Module effort: set up alias + implement v-if in the page

Pros & Cons

✓ What works well

  • No rebuild or restart required to toggle
  • Reactive in the browser — same tab updates instantly on toggle
  • Route guarding and block filtering are invisible to module authors
  • Extension list is production-safe (baked into server bundle at build time)
  • Single flag file used consistently by all readers/writers
  • Default is always enabled — absent flag never accidentally disables

✗ Known limitations

  • Route guard is client-side only — direct URL to a disabled page still SSR-renders before redirecting (flash)
  • Module is always compiled into the bundle — flag control does not reduce JS payload
  • Slot injection requires PWA to explicitly place <UiExtensionSlot> — modules can't inject into arbitrary locations
  • Page override fallback requires module author to write v-if — no framework enforcement
  • Component-level reactive behavior (timers, banners) must be wired manually per module
